# 2차 개선 계획

## 목적

1차 개선은 프로젝트 실행 복구, 구조 정리, 인증/권한, API 계약, 테스트, DB migration 기반을 만드는 작업이었다.

2차 개선은 서비스 완성도와 포트폴리오 설득력을 높이는 작업이다. 핵심 방향은 다음과 같다.

- 하드코딩과 임시 설계를 줄인다.
- 실제 API 경계에서 검증을 늘린다.
- 사용자 입력 검증과 에러 응답을 일관화한다.
- README와 문서가 포트폴리오에서 바로 설명 가능한 형태가 되도록 보강한다.

## P1. AI 기본 category ID 제거

현재 `ScheduleCommandService`는 AI가 생성하는 Task/Calendar에 기본 category ID `1`을 사용한다.

문제:

- DB 초기 상태에 category ID `1`이 없으면 AI 생성이 실패할 수 있다.
- 특정 사용자 소유 category인지 보장하지 못한다.
- 테스트와 배포 환경에서 재현성이 떨어진다.

개선 방향:

- 사용자별 기본 category를 조회하거나 없으면 생성한다.
- AI 요청에서 category를 추론할 수 있으면 해당 category를 사용한다.
- category 결정 책임을 별도 service로 분리한다.

성공 기준:

- AI 생성 흐름이 category ID `1`에 의존하지 않는다.
- 사용자별 category owner 검증을 통과한다.
- OpenAI API 호출 없이 관련 service test가 통과한다.

## P1. Controller 통합 테스트 확대

현재는 일부 service 단위 테스트와 Task controller session 인증 테스트가 있다.

추가할 테스트:

- 인증 없이 보호 API 호출 시 `401`
- 다른 사용자 리소스 수정/삭제 시 `403`
- 로그인 사용자 기준 Task CRUD 성공
- 로그인 사용자 기준 Calendar CRUD 성공
- Category 생성/조회/수정/삭제 성공

성공 기준:

- controller-service-repository 경계에서 최소 CRUD 흐름을 검증한다.
- owner 검증 실패가 실제 HTTP 응답으로 확인된다.

## P1. API contract 동기화

현재 `docs/계약/API_계약.md`에 주요 API 계약을 정리했다.

추가 점검:

- 문서의 request/response field가 실제 DTO와 일치하는지 확인.
- controller 변경 시 API 계약 문서도 함께 갱신하는 규칙 추가.
- legacy path를 유지하는 API는 명시적으로 표시.

성공 기준:

- 문서만 보고 로컬 API를 호출할 수 있다.
- 실제 controller path와 문서 path가 일치한다.

## P2. API/Validation/Exception 정리

대상:

- Category API RESTful path 정리
- Calendar search API 정리
- DTO validation 추가
- `GlobalExceptionHandler` 보강

개선 방향:

- `POST /api/categories`
- `GET /api/categories`
- `PUT /api/categories/{categoryId}`
- `DELETE /api/categories/{categoryId}`
- search 조건은 query parameter 또는 `POST /search` request body로 정리
- validation 실패, 인증 실패, 권한 실패, not found 응답 형식을 통일

성공 기준:

- API path naming이 Task/Calendar/Category 사이에서 일관된다.
- 프론트 호출도 새 contract에 맞게 변경된다.
- validation 실패가 400과 명확한 메시지로 반환된다.

## P2. DB migration 후속 정리

현재 Flyway는 도입했고, 기존 DB는 baseline 처리했다.

남은 정리:

- `category_id_category_id`, `user_id_user_id` 같은 join column 이름 개선 여부 결정.
- column rename은 별도 migration으로 분리.
- 기존 로컬 DB를 유지할지, 새 migration 기준으로 초기화할지 결정.

성공 기준:

- Entity field와 DB column naming 전략이 문서화된다.
- schema 변경은 Hibernate `update`가 아니라 Flyway migration으로만 수행된다.
