# 1차 구조 진단

## 결론

프로젝트는 현재 실행 가능한 상태까지 복구되어 있다. 다만 실제 서비스 코드 기준으로는 인증, 사용자 식별, CORS, 테스트 부재가 가장 큰 리스크다. 바로 대규모 리팩터링에 들어가기보다, 먼저 인증/쿠키 처리와 API 호출 방식을 정리한 뒤 도메인 모델과 프론트 구조를 단계적으로 손보는 편이 안전하다.

## 현재 상태

| 항목 | 상태 |
|---|---|
| 구조 | `frontEnd/`, `backEnd/`, `docs/`로 분리됨 |
| 백엔드 | Spring Boot 3.3.4, Java 17, Maven wrapper |
| 프론트 | Create React App, React 18 |
| DB | Docker MySQL의 `timetodo` DB 사용 |
| 환경변수 | `backEnd/.env`로 DB credential과 OpenAI key 분리 |
| 검증 | 백엔드 build, 프론트 build, 백엔드 8085 기동 확인 |

## 즉시 수정 후보

### 1. 로그인 실패 시 NullPointerException 가능

`authenticateUser()`가 인증 실패 시 `null`을 반환하고, Controller가 바로 `authenticatedUser.getUserId()`를 호출한다.

- 위치: `backEnd/src/main/java/org/timetodo/service/UserServiceImpl.java:79`
- 위치: `backEnd/src/main/java/org/timetodo/controller/UserController.java:47`
- 영향: 잘못된 로그인 요청이 401이 아니라 500으로 터질 수 있다.
- 제안: 인증 실패는 `ResponseEntity.status(HttpStatus.UNAUTHORIZED)`로 명시 처리한다.

### 2. 비밀번호 평문 저장과 평문 비교

회원가입 시 비밀번호를 그대로 저장하고, 로그인 시 문자열 비교를 한다.

- 위치: `backEnd/src/main/java/org/timetodo/service/UserServiceImpl.java:36`
- 위치: `backEnd/src/main/java/org/timetodo/service/UserServiceImpl.java:81`
- 영향: DB가 노출되면 계정 비밀번호가 즉시 노출된다.
- 제안: `BCryptPasswordEncoder` 기반 hash 저장으로 교체한다. 기존 개발 DB는 초기화하거나 임시 migration을 둔다.

### 3. userId 쿠키를 인증 수단처럼 사용

서버가 `userId`를 쿠키에 저장하고, 다른 API는 해당 값을 신뢰해 사용자 데이터를 조회한다.

- 위치: `backEnd/src/main/java/org/timetodo/controller/UserController.java:50`
- 위치: `backEnd/src/main/java/org/timetodo/controller/TaskController.java:92`
- 위치: `backEnd/src/main/java/org/timetodo/controller/CalendarController.java:89`
- 영향: 클라이언트가 쿠키 값을 바꾸면 다른 사용자의 데이터에 접근할 수 있다.
- 제안: 최소한 서버 세션 기반으로 사용자 식별을 옮기고, 장기적으로 Spring Security 기반 인증으로 전환한다.

### 4. CORS가 credential 허용 상태에서 전체 origin 허용

`allowedOriginPatterns("*")`와 `allowCredentials(true)`가 함께 설정되어 있다.

- 위치: `backEnd/src/main/java/org/timetodo/config/WebConfig.java:15`
- 위치: `backEnd/src/main/java/org/timetodo/config/WebConfig.java:18`
- 영향: 개발 중에는 편하지만 credential 기반 요청과 조합하면 위험하다.
- 제안: 로컬 개발 기본값은 `http://localhost:3000`만 허용하고, 필요 시 env로 허용 origin을 주입한다.

### 5. 수정/삭제 API에서 소유자 검증이 없다

조회/생성은 쿠키에서 userId를 읽지만, update/delete는 요청 body의 ID만으로 처리된다.

- 위치: `backEnd/src/main/java/org/timetodo/controller/TaskController.java:123`
- 위치: `backEnd/src/main/java/org/timetodo/controller/TaskController.java:141`
- 위치: `backEnd/src/main/java/org/timetodo/controller/CalendarController.java:118`
- 위치: `backEnd/src/main/java/org/timetodo/controller/CalendarController.java:129`
- 영향: ID만 알면 다른 사용자의 task/calendar를 수정하거나 삭제할 수 있다.
- 제안: 모든 변경 API에서 현재 사용자와 resource owner를 함께 검증한다.

## 단기 정리 후보

### 1. 프론트 API 호출 방식이 섞여 있음

상대 경로 `/api/...`, 절대 경로 `http://localhost:8085/...`, `fetch`, `axios`가 혼재되어 있다.

- 위치: `frontEnd/src/components/home/TodayTodo.js:19`
- 위치: `frontEnd/src/components/home/TodayTodo.js:36`
- 위치: `frontEnd/src/components/login/Login.js:21`
- 영향: 개발/배포 환경 전환이 어렵고 credential 설정이 누락되기 쉽다.
- 제안: `src/api/client.js` 같은 axios instance를 만들고 `baseURL`, `withCredentials`를 한 곳에서 관리한다.

### 2. 프론트에 존재하지만 백엔드에 없는 API가 있음

`/api/schedule/add`, `/api/schedule/list`를 호출하지만 백엔드에는 대응 controller가 없다.

- 위치: `frontEnd/src/components/ai/ScheduleInput.js:9`
- 위치: `frontEnd/src/components/ai/ScheduleList.js:9`
- 영향: 해당 기능은 항상 실패한다.
- 제안: 사용하지 않는 컴포넌트면 제거 후보로 표시하고, 필요한 기능이면 백엔드 API 계약부터 정의한다.

### 3. 테스트가 사실상 없음

백엔드 테스트 파일은 통째로 주석 처리되어 있다.

- 위치: `backEnd/src/test/java/org/timetodo/TimeTodoApplicationTests.java:1`
- 영향: 리팩터링 안전성이 낮다.
- 제안: 우선 `UserController`, `TaskService`, `CalendarService`의 최소 단위 테스트부터 복구한다.

### 4. Spring 설정이 개발 환경에 고정되어 있음

`ddl-auto=update`, `show-sql=true`, `open-in-view=true`가 기본 설정이다.

- 위치: `backEnd/src/main/resources/application.properties:14`
- 위치: `backEnd/src/main/resources/application.properties:16`
- 위치: `backEnd/src/main/resources/application.properties:17`
- 영향: 운영 전환 시 schema drift, 과도한 SQL 로그, lazy loading 의존이 생길 수 있다.
- 제안: `local` profile과 기본 profile을 분리한다.

### 5. Controller마다 쿠키 추출 로직이 중복됨

Task, Calendar, Category, Preferences, Chat controller가 각각 `userId` 쿠키를 읽는다.

- 영향: 예외 처리와 인증 정책이 파일마다 달라진다.
- 제안: 단기적으로 `CurrentUserResolver` 또는 공통 helper를 만들고, 장기적으로 Spring Security로 대체한다.

## 장기 리팩터링 후보

### 1. 인증 구조 재설계

현재는 클라이언트 상태 `isAuthenticated`와 `userId` 쿠키에 의존한다.

- 위치: `frontEnd/src/App.js:15`
- 영향: 새로고침 시 로그인 상태가 사라지고, 서버 인증과 프론트 인증 상태가 일치하지 않는다.
- 제안: 서버 세션 또는 token 기반 인증을 선택하고 `/api/user/me` 같은 인증 확인 API를 둔다.

### 2. Entity 관계와 naming 정리

`TaskEntity.userId`처럼 필드명은 ID처럼 보이지만 실제 타입은 `UserEntity`다.

- 위치: `backEnd/src/main/java/org/timetodo/entity/TaskEntity.java`
- 위치: `backEnd/src/main/java/org/timetodo/entity/CalendarEntity.java`
- 영향: DTO 변환, query method, JSON 응답에서 혼동이 커진다.
- 제안: `user`, `category`, `reminders`처럼 객체 관계 이름으로 바꾼다.

### 3. DTO와 Entity 응답 경계 정리

일부 API는 DTO를 반환하고, 일부 update API는 Entity를 그대로 반환한다.

- 위치: `backEnd/src/main/java/org/timetodo/controller/TaskController.java:123`
- 위치: `backEnd/src/main/java/org/timetodo/controller/CalendarController.java:118`
- 영향: JSON 순환 참조, 불필요한 필드 노출, 프론트 의존성 증가 가능성이 있다.
- 제안: API 응답은 DTO로 통일한다.

### 4. AI 기능과 도메인 기능 분리

OpenAI 호출, 응답 parsing, Task/Calendar 생성, log 저장이 한 서비스에 섞여 있다.

- 위치: `backEnd/src/main/java/org/timetodo/ai/OpenAIService.java`
- 영향: AI 응답 형식 변경 시 일정/할일 생성까지 같이 깨진다.
- 제안: `AiClient`, `AiParsingService`, `ScheduleCommandService`로 책임을 분리한다.

## OpenCode 인계 후보

OpenCode에 넘기기 좋은 작업은 아래 순서다.

1. 인증/권한 리스크 전체 코드 리뷰
2. 프론트 API 호출 통일 작업 범위 산정
3. Entity/DTO/API 계약 정리안 작성
4. 테스트 전략과 최소 테스트 세트 설계
5. AI 기능 분리 설계안 작성

## 권장 진행 순서

1. 로그인 실패 500 문제와 비밀번호 hash 처리부터 수정한다.
2. CORS와 cookie 설정을 로컬 개발 기준으로 좁힌다.
3. userId 쿠키 직접 신뢰 구조를 서버 세션 또는 Spring Security 기반으로 바꾼다.
4. 프론트 API client를 만들고 `/api` 호출을 한 곳으로 모은다.
5. `Task`, `Calendar`, `Category`의 수정/삭제 소유자 검증을 추가한다.
6. 최소 테스트를 추가한 뒤, Entity/DTO 리팩터링으로 넘어간다.

## 이번 진단에서 검증한 명령

```bash
cd backEnd && bash ./mvnw -DskipTests package
cd frontEnd && npm run build
cd backEnd && timeout 25s bash ./mvnw spring-boot:run
```

세 명령은 폴더 구조 변경 이후 성공한 것을 확인했다.
